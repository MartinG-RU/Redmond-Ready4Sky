# ESPHome-Ready4Sky — исправленная рабочая копия

Шлюз ESP32/ESPHome для Bluetooth-приборов REDMOND Ready4Sky и Home Assistant. Основан на [KomX/ESPHome-Ready4Sky](https://github.com/KomX/ESPHome-Ready4Sky), исходный коммит `2c96fc402168f0d8f7f5a63f2032c36decbdd08f`. Это модифицированная копия, а не официальный релиз автора.

> **Важно:** физические приборы и ESP32 с этой версией не испытывались. Успешная сборка, проверка конфигураций и тесты протокольного кода не доказывают совместимость с конкретным прибором. Первые испытания выполняйте под наблюдением; не полагайтесь на шлюз как на аварийное выключение. Датчик дыма через `skysmoke` **не может быть единственным каналом пожарной безопасности**.

## Что входит и что не поддерживается

Девять драйверов: `skykettle`, `skyplug`, `skycoffee`, `skycooker`, `skybaker`, `skydew`, `skyheat`, `skyiron` и `skysmoke`. Список названий моделей находится в `MODEL_TYPE` файла `components/<компонент>/__init__.py`. Валидация названия или компиляция не является проверкой конкретной модели на железе.

* `skyoven` **не реализован**: в исходном проекте отсутствуют C++-драйвер и описание протокола. Конфигурация будет отклонена с понятной ошибкой.
* Нагреватели **RCH-4560S, RFH-C4519S, RFH-C4522S** (в том числе варианты с кириллической `С`) отклоняются: для безопасной реализации нужны достоверные трассы протокола. У других моделей `skyheat` настройка `target_temperature` также не реализована и отклоняется. Не приравнивайте ограниченную поддержку к гарантии безопасности нагревателя.
* Настройки, не реализованные для выбранной модели чайника или кофеварки, отвергаются при проверке. Например, регулировка времени кипения доступна в коде лишь для типов `0x08`/`0x10`. Цветная подсветка, последовательность её команд и отображение требуют проверки на реальном чайнике.
* Типы чайников RK-M173S/M173S-E изменены на ветку типа M170S по комментариям исходного кода; это **предположение**, требующее испытания. Синхронизация времени, интерпретация часового пояса и переходов DST, сканирование и восстановление BLE также не проверены на оборудовании.
* В старых README отдельных компонентов перечислены модели, которые проверял **автор исходного проекта**, а не автор этой переработки. Некоторые старые примеры могут содержать теперь запрещённые или неподдерживаемые параметры; ориентируйтесь на вывод `esphome config` и данный README.

## Подключение по ссылке GitHub

После публикации **своего** репозитория замените источник в YAML на `github://ВАШ-АККАУНТ/ИМЯ-РЕПОЗИТОРИЯ@main`. Подробная инструкция и пример для SkyCoffee: [GITHUB-INSTALL.md](GITHUB-INSTALL.md). При изменении источника сохраните другие настройки YAML, очистите build-файлы и соберите свою прошивку. Использование Git-ссылки само по себе не обновляет уже прошитую ESP32.

## Подключение локальной копии

Если у вас компоненты уже находятся в `config/esphome/ESPHome-Ready4Sky/components`, следуйте пошаговой инструкции [LOCAL-INSTALL.md](LOCAL-INSTALL.md). Это компоненты для уже установленного ESPHome, а не содержимое `/config/custom_components/`.

1. Распакуйте архив целиком. В примере путь `../components` разрешается относительно YAML в каталоге `examples/`, поэтому при перемещении YAML исправьте `path` на путь к **этой** папке `components`. Не используйте в качестве источника исходный URL KomX: он загрузит неисправленную версию.
2. Скопируйте `examples/secrets.example.yaml` в `examples/secrets.yaml`, задайте Wi-Fi и уникальный 32-байтовый Base64-ключ шифрования ESPHome API. Например, ключ можно создать командой `openssl rand -base64 32`. Не публикуйте свой `secrets.yaml`.
3. В `examples/esp32-kettle-plug.yaml` замените оба примерных MAC-адреса и модели на свои. Адреса в примере — заглушки. Посмотрите доступные настройки в README соответствующего драйвера и в его схеме.
4. В окружении с Python 3.13 установите `esphome==2026.10.1`. Выполните проверку и, только после исправления заглушек, соберите свою конфигурацию:

   ```sh
   esphome config examples/esp32-kettle-plug.yaml
   esphome compile examples/esp32-kettle-plug.yaml
   # прошивку выполняйте только для своей ESP32 и проверенного конфига
   # esphome run examples/esp32-kettle-plug.yaml
   ```

ESPHome устанавливает дополнительные компоненты toolchain при первой сборке. В Home Assistant OS/ESPHome путь к локальным файлам должен существовать внутри контейнера аддона, обычно под его каталогом конфигурации. Для своего Git-форка можно вместо `type: local` указать Git-источник **своего** форка и фиксированный `ref`.

## Практические ограничения

* `ready4sky` самостоятельно управляет BLE. Не используйте в той же конфигурации `esp32_ble_tracker`, `esp32_ble` или функции, которые их подгружают (в частности, Bluetooth Proxy): они конфликтуют с этим движком.
* У каждого прибора должен быть свой MAC. Схема проверяет повторения, имена моделей, интервалы сканирования и ряд несовместимых настроек. Одновременное подключение к телефону/другому шлюзу может препятствовать связи.
* Для ESP32 с ESP-IDF схема разрешает до 9 приборов суммарно и запрашивает соответствующую ёмкость BLE-контроллера; для ESP32-C2 — до 2, для Arduino — до 3. Это лишь конфигурационные пределы, не гарантия устойчивой работы или свободной памяти. У каждого драйвера сохраняется собственный `MULTI_CONF` в его схеме. Если приборов много, практичнее распределить их по нескольким шлюзам.
* ESP32-S2 не имеет Bluetooth и отклоняется. Фактически компиляция проверена только для `esp32dev`/ESP32 с ESP-IDF; другие платы и Arduino не проверялись.
* Команды складываются в ограниченную очередь из 8 снимков с параметрами. При переполнении новая команда отклоняется с записью в лог; при потере связи очередь очищается. Выключение приоритетно отменяет ожидающие команды, но не может отменить уже отправленную команду и **не гарантировано при разрыве BLE**. Сверяйте фактическое состояние прибора.
* При разрыве связи состояния большинства других приборов могут остаться последними полученными значениями, а не стать недоступными. Не считайте их подтверждением текущего состояния.
* При потере связи `skysmoke` помечает показания недоступными, а не сообщает «дыма нет». Проверка на устройстве не выполнялась; также настройте независимый сертифицированный канал оповещения.
* MAC и имя прибора используются в алгоритме авторизации устройства и не являются надёжным секретом; режим BLE, сохранённый от upstream, не гарантирует защиту от MITM. Сегментируйте сеть, используйте шифрование API и не размещайте шлюз в недоверенной сети.

## Проверки разработки

В рабочем окружении использовались ESPHome `2026.10.1`, `esp32dev` и ESP-IDF. Выполненные сборки и их точные версии описаны в `TESTING.md`.

```sh
python -m pip install 'esphome==2026.10.1' pytest
python -m pytest tests/test_schema.py -q
bash tests/native/run.sh
esphome compile tests/all-drivers-native.yaml
# альтернативный toolchain:
esphome compile tests/all-drivers.yaml
```

`tests/all-drivers*.yaml` — **только тестовые матрицы компиляции** с синтетическими MAC и фиктивным Wi-Fi. Их нельзя прошивать и использовать как конфигурацию реальных приборов. Тесты с ASan/UBSan используют реальные исходники нескольких драйверов и BLE-движка с программными заглушками. Симулятор не моделирует радиосвязь, реальную многозадачность или все пути выполнения. В GitHub Actions предусмотрены проверки схем, host-регрессий и обеих сборок.
